# `gop shell install|uninstall` Spec

## Purpose

`gop shell install` and `gop shell uninstall` make the existing `gop cd` shell integration persistent and maintainable. They solve the update and removal problems of manually adding `eval "$(gop shell init ...)"` to a shell startup file.

The commands install a small managed source block into the user's shell startup file and store the generated Git Outpost shell function in a Git Outpost-owned file. Re-running `install` updates that generated file and replaces the managed source block. Running `uninstall` removes only Git Outpost's managed source block and generated file.

This milestone also adds a dummy binary `gop cd [<outpost>]` command for discoverability and setup guidance. After shell integration is active, the shell function shadows the binary and handles `gop cd` before the binary sees it.

## Dependencies

This spec depends on [2026-07-03-gop-shell-cd-spec.md](2026-07-03-gop-shell-cd-spec.md).

`gop shell install` must reuse the shell function generated by `gop shell init [bash|zsh]`. It must not duplicate or reinterpret `gop cd` behavior.

## Scope

This spec covers:

```bash
gop cd [<outpost>]
gop shell install <bash|zsh>
gop shell uninstall <bash|zsh>
gop shell install <bash|zsh> --rc-file <path> --script-file <path>
gop shell uninstall <bash|zsh> --rc-file <path> --script-file <path>
```

The explicit shell kind is required for `install` and `uninstall` because these commands edit shell-specific startup files. `gop shell init` may keep its existing optional shell argument because it only prints shell code.

This spec does not add Fish, PowerShell, Nushell, automatic shell detection, prompts, backup files, migration of manually pasted `gop shell init` snippets, or a binary implementation that changes directories.

## Dummy `gop cd` Behavior

The binary command `gop cd [<outpost>]` exists only to make the feature visible in root help and to guide users who have not enabled shell integration.

The binary command must not attempt to change directories. A child process cannot change its parent shell's current working directory.

When invoked as `gop cd` or `gop cd <outpost>` without shell-function interception, the binary prints setup guidance to stderr and exits non-zero. The guidance must explain that `gop cd` is provided by shell integration and show both temporary setup and persistent setup:

```text
eval "$(gop shell init bash)"
eval "$(gop shell init zsh)"
gop shell install bash
gop shell install zsh
```

`gop cd --help` exits successfully and explains the same shell-integration requirement.

The dummy binary command must not require a source repository or outpost context. It must not resolve `<outpost>`, call `gop path`, inspect Git state, or mutate files.

## Default Paths

For Bash, the default startup file is:

```text
$HOME/.bashrc
```

For Zsh, the default startup file is:

```text
$HOME/.zshrc
```

The default generated script directory is:

```text
$XDG_CONFIG_HOME/git-outpost
```

If `XDG_CONFIG_HOME` is unset or empty, the default generated script directory is:

```text
$HOME/.config/git-outpost
```

The default generated script files are:

```text
shell.bash
shell.zsh
```

under that generated script directory.

`--rc-file <path>` overrides the startup file. `--script-file <path>` overrides the generated script file. Relative override paths are resolved against Git Outpost's effective current directory, including the global `-C <path>` behavior.

## Install Behavior

`gop shell install <shell>` writes the current `gop shell init <shell>` output to the selected generated script file.

It then ensures the selected startup file contains exactly one Git Outpost-managed source block:

```sh
# >>> git-outpost shell install >>>
# Managed by Git Outpost. Remove with: gop shell uninstall <shell>
# Sources the generated Git Outpost shell integration.
if [ -f '<script-file>' ]; then
    . '<script-file>'
fi
# <<< git-outpost shell install <<<
```

The actual script path must be shell-quoted safely.

If the startup file has no managed source block, `install` appends one. If it already has exactly one managed source block, `install` replaces it. This makes `gop shell install <shell>` the update command.

`install` must create parent directories for the generated script file. It may create the startup file if it does not exist. It must not require a source repository or outpost context.

On success, `install` prints the installed shell kind, startup file path, and generated script path.

## Uninstall Behavior

`gop shell uninstall <shell>` removes the Git Outpost-managed source block from the selected startup file, if present.

It also removes the selected generated script file, if present.

`uninstall` is idempotent. If neither the managed source block nor the generated script file exists, it exits successfully and reports that the selected shell integration was not installed.

`uninstall` must not remove:

- manually pasted `gop shell init` output,
- manually added `eval "$(gop shell init ...)"` lines,
- shell aliases,
- unrelated startup file content,
- generated script files for other shells.

On success, `uninstall` prints the uninstalled shell kind, startup file path, and generated script path.

## Safety And Errors

`install` and `uninstall` own only the block between these markers:

```sh
# >>> git-outpost shell install >>>
# <<< git-outpost shell install <<<
```

If a startup file contains a start marker without an end marker, an end marker without a start marker, or multiple managed source blocks, the command must fail without modifying the startup file. The diagnostic should point at the startup file and explain the marker problem.

Unsupported shell names must fail through CLI argument parsing before any file is changed.

If `$HOME` is required for default path resolution and is unset or empty, the command must fail before any file is changed.

File IO failures must use the existing CLI error path and include the relevant path.

## Documentation Requirements

The README and product documentation must present `gop shell install <bash|zsh>` as the recommended persistent setup path.

The documentation must keep `gop shell init [bash|zsh]` as the current-shell and scriptable primitive.

The documentation must explain that:

- rerunning `gop shell install <shell>` updates the generated shell integration,
- `gop shell uninstall <shell>` removes only Git Outpost's managed source block and generated script,
- manual `eval "$(gop shell init ...)"` lines remain manual and are not removed by `uninstall`.

The command reference, synopsis, working-directory matrix, and roadmap must include the dummy `cd` command, `shell install`, and `shell uninstall`.

## Test Requirements

Help tests must include the root `cd` command, `gop cd --help`, `shell install`, and `shell uninstall`, their required `SHELL` argument, and the `--rc-file` and `--script-file` options.

CLI behavior tests must cover:

- `gop cd` without shell integration exits non-zero and prints setup guidance,
- `gop cd <outpost>` without shell integration exits non-zero and prints setup guidance without resolving the outpost,
- installing Bash integration into explicit test paths,
- installing Zsh integration into explicit test paths,
- replacing an existing managed source block on repeated install,
- updating the generated script file on repeated install,
- uninstalling removes the managed block and generated script,
- uninstalling is idempotent when nothing is installed,
- uninstalling does not remove manually pasted `gop shell init` output,
- malformed managed markers fail without modifying the startup file,
- relative `--rc-file` and `--script-file` paths honor global `-C`.

Shell smoke tests must prove that a shell can source the installed startup file and then use `gop cd`.
